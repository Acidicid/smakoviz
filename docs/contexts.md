# Предметна область і межі контекстів (Bounded Contexts)

## Домен

**SmakoViz** — сервіс доставки їжі з ресторанів міста.
Користувачі: **клієнти** (замовляють їжу й пишуть відгуки), **ресторани** (ведуть меню, приймають і готують замовлення, відповідають в обговореннях), **кур'єри** (везуть замовлення), **модератори** (стежать за обговореннями).
Система дає змогу швидко оформити замовлення, бачити його статус у реальному часі й обирати ресторан за чесними оцінками.

## Контексти

Принцип: **кожна сутність належить рівно одному контексту**. Інші контексти знають про неї лише за Id
(+ знімок або копія окремих полів — див. [duplication-policy.md](duplication-policy.md)).

### 1. Доставка (DeliveryOrders) — Проєкт №1, `SmakoViz_Delivery`, SQL Server + ADO.NET/Dapper

| Сутність | Роль |
|----------|------|
| `Customer` | клієнт сервісу (email, ім'я, телефон) — **власник даних про клієнта** |
| `DeliveryOrder` | корінь агрегату «Замовлення доставки»: номер, статус, суми |
| `DeliveryDetails` | адреса, телефон, коментар кур'єру (1:1 із замовленням) |
| `OrderLine` | позиція замовлення зі **знімком** назви й ціни страви |
| `OrderStatusHistory` | журнал переходів статусу |
| `Dish` *(копія)* | локальна read-копія страв Меню для перевірки ціни/доступності — **не власна сутність**, не редагується тут |

**Агрегат «Замовлення доставки»** = `DeliveryOrder` + `DeliveryDetails` + `OrderLine[]` + `OrderStatusHistory[]`.
Позиції, деталі й історія не існують без замовлення (`ON DELETE CASCADE`) і змінюються лише через процедури замовлення.
**Агрегат «Клієнт»** = `Customer` (окремий, бо має власний життєвий цикл; клієнта з історією не видаляють).

Життєвий цикл замовлення:

```
Placed ──► Confirmed ──► Paid ──► Cooking ──► OnTheWay ──► Delivered
   │            │
   └────────────┴──► Cancelled        (скасування лише ДО оплати)
```

### 2. Меню (Menu) — Проєкт №2, `SmakoViz_Menu`, SQL Server + EF Core

| Сутність | Роль |
|----------|------|
| `Restaurant` | ресторан-партнер — **власник назви ресторану** |
| `RestaurantProfile` | адреса, години роботи, мінімальна сума (1:1) |
| `Dish` | страва — **власник назви, ціни, доступності** |
| `Category` | довідник категорій (Піца, Напої, Хіт продажу…) |
| `DishCategory` | M:N страва↔категорія з полями `AddedAt`, `IsFeatured` |

**Агрегат «Ресторан»** = `Restaurant` + `RestaurantProfile`.
**Агрегат «Страва»** = `Dish` + `DishCategory[]` (страва знає свої категорії).
`Category` — окремий довідник.

### 3. Відгуки (Feedback) — Проєкт №3, `smakoviz_feedback`, MongoDB

| Сутність (колекція) | Роль |
|---------------------|------|
| `Review` (`reviews`) | відгук на страву / ресторан / кур'єра; оцінка 1–5, текст, фото, коментарі |
| `Discussion` (`discussions`) | тема обговорення біля ресторану або відгуку |
| `Message` (`messages`) | повідомлення в обговоренні |
| `RatingSummary` (`ratingSummaries`) | підсумкові оцінки ресторану (read-model) |

**Агрегат «Відгук»** = документ `reviews` з вбудованими `author` і `comments[]` (їх мало і вони завжди читаються разом).
**Агрегат «Обговорення»** = `discussions` + `messages` (повідомлень може бути тисячі, тому вони в окремій колекції за посиланням; у самому обговоренні — лише прев'ю трьох останніх).

## Взаємодія контекстів (без спільних баз)

```
            DishChanged / RestaurantRenamed (події)
   ┌──────────── Меню ─────────────┐
   ▼                               ▼
Доставка ───── CustomerRenamed ──► Відгуки
 (Id замовлення/клієнта в відгуку — лише посилання)
```

- Доставка тримає копію страв, щоб при кожному додаванні в кошик не викликати Меню синхронно.
- Відгуки тримають копії назв, щоб сторінка відгуків рендерилась без звернень до Меню й Доставки.
- Ціна/назва в позиції замовлення — знімок: зміна меню не «переписує» старі чеки.
